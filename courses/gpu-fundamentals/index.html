Part I · GPU foundations and Hopper architecture

1. Decide whether work belongs on a GPU

Outcome. Explain the CPU/GPU trade and measure the crossover without hiding transfer or launch cost.
Recall first. Why can a massively parallel GPU lose to a CPU on a small tensor even when the GPU has much higher peak arithmetic throughput?

A CPU is designed to reduce the latency of a small number of complicated instruction streams. Large caches, speculative execution, and sophisticated branch prediction serve irregular control work well. A GPU devotes more area to parallel arithmetic and throughput. It wins when many similar operations can run together long enough to amortize command launch and data movement.

Three measurements answer three different questions. CPU time describes the host implementation. Resident GPU time assumes inputs and outputs already live on the device, as in a steady training loop. Transfer-inclusive GPU time includes required copies and represents one-shot offload or an application boundary. Never subtract transfers from an end-to-end claim merely because the kernel looks fast.

Batching changes the balance. Combining many small items can increase parallel work per launch, improve matrix shape, and reduce Python overhead per item. Batching can also increase queueing latency or memory pressure. “Use a larger batch” is therefore a hypothesis tied to a service objective, not a universal rule.

Workload traitCPU is attractiveGPU is attractive
Amount of workTiny or occasionalLarge or repeatedly batched
Control flowIrregular and branch-heavyRegular across many elements
Data locationAlready in host memoryAlready resident on device
Latency goalOne small operationHigh aggregate throughput

Worked example

A vector expression over 1,024 elements launches CUDA work but exposes little parallel work. The same expression over millions of resident elements has enough threads to occupy many SMs. If the input is copied to the GPU and the result copied back every time, the crossover moves again. The correct lab records all three paths across sizes; it does not claim one permanent threshold.

Practice

Before running Lab 01, predict which path will win for the smallest size and which cost dominates transfer-inclusive GPU time. After running, identify the first size where the ranking changes. Repeat once with a different iteration count without changing tensor values or dtypes.

Check your reasoning

The small CPU path often wins because launch and synchronization are fixed costs. Resident GPU work should become more competitive as parallel work grows. Transfer-inclusive behavior depends on the allocation and interconnect, so the answer is the measured crossover, not a memorized number. Changing only the iteration count should affect confidence and overhead amortization, not the definition of each path.

Review cue. When a later optimization proposes offload, ask whether its comparison matches resident or transfer-inclusive use.

2. Read the H100 device from HBM to streaming multiprocessors

Outcome. Locate the major device-wide components that move, cache, schedule, and execute a PyTorch workload.
Recall first. Which costs belong outside a GPU kernel: host preparation, launch, host-to-device transfer, and inter-node communication?

An H100 is not one large arithmetic unit. At the system boundary, a CPU prepares work and reaches the GPU through PCIe. Device memory is implemented with HBM stacks and memory controllers. A device-wide L2 cache and on-chip interconnect serve many groups of execution resources. Graphics Processing Clusters (GPCs) group Texture Processing Clusters (TPCs), and a Hopper TPC contains two Streaming Multiprocessors (SMs). CUDA thread blocks execute on SMs.

The hierarchy matters because distance and sharing change the cost. HBM is large and device-wide but farther from execution. L2 is also device-wide and can reuse data across SMs. Resources inside an SM are faster and smaller. A block normally remains on one SM for its lifetime, so its registers and ordinary shared memory do not become a device-wide store. Hopper thread-block clusters add controlled cooperation across nearby SMs within a GPC, but they do not turn every SM resource into global memory.

The full GH100 design and shipping H100 products do not enable identical numbers of GPCs, TPCs, SMs, memory controllers, or HBM stacks. The SXM and PCIe products also differ. Therefore the diagram shows containment and data paths, not an exact floorplan. Query the allocated GPU for its product name, compute capability, total memory, and SM count; do not infer disabled units from a marketing diagram.

Worked example

A tensor already in HBM does not pay a new PCIe copy for every kernel. A load instruction issued by an SM requests data through its cache hierarchy; an L2 hit can avoid an HBM access. A separate input pipeline may concurrently copy the next batch through PCIe. Those are different paths and require different measurements.

Practice

From Lab 00, record the exact product name, compute capability, total memory, SM count, and MIG state. Annotate the diagram with only the properties the runtime reports. Mark GPC/TPC counts as unknown unless the specific official product documentation establishes them.

Check your reasoning

A correct annotation separates detected facts from architecture-family facts. Compute capability 9.0 identifies Hopper H100 behavior, while the product name and runtime properties identify the allocated SKU. The logical HBM/L2/GPC/TPC/SM hierarchy is reusable; exact enabled-unit counts are not universal.

Review cue. For every later bottleneck, state whether its limiting resource is system-wide, device-wide, GPC-local, SM-wide, or local to a thread or block.

3. Look inside a Hopper streaming multiprocessor

Outcome. Distinguish per-thread, per-block, scheduler-partition, and SM-wide resources that constrain a kernel.
Recall first. Which device components are shared by all SMs, and which resources must be allocated before a block can reside on one SM?

A Hopper SM is divided into four scheduler/execution subpartitions, often called SMSPs. Each has a warp scheduler and a share of the execution pipelines and register-file implementation. At the compute-capability 9.0 programming-model level, one SM has four warp schedulers, 128 FP32 units, 64 FP64 units, 64 INT32 units, 16 special-function units, and four fourth-generation Tensor Cores. These totals describe available pipelines; they do not mean one warp uses every unit at once.

Registers are logically private to threads, but their physical capacity is finite and allocated across resident warps. Shared memory is explicitly allocated per thread block and is visible to threads in that block. Hopper implements shared memory and L1/texture caching from a unified 256 KB physical resource; the shared-memory carveout can be configured up to 228 KB per SM, with at most 227 KB available to one opted-in block. Increasing registers per thread or shared memory per block can reduce how many blocks and warps reside simultaneously.

A warp scheduler chooses among its assigned resident warps. A resident warp may be stalled, eligible, selected, or issued. The scheduler can hide one warp's latency by issuing an eligible instruction from another, but only if independent work exists and required execution pipelines are available. Tensor Cores execute eligible matrix instructions; ordinary FP/INT pipelines execute other instructions. TMA can move multidimensional tiles between global and shared memory asynchronously for compatible kernels.

Worked example

Suppose a kernel doubles its registers per thread. It may reduce spills and execute each warp more efficiently, but fewer warps may fit on the SM. Conversely, forcing fewer registers may raise occupancy while creating local-memory spills backed by device memory. The winning point is the measured balance, not the largest occupancy percentage.

Practice

For one kernel from Lab 08 or 09, classify every item as thread-private, block-scoped, SMSP scheduled, SM-wide, or device-wide: registers, a warp, shared memory, L1, Tensor Core instructions, L2, and HBM. Then predict which resource could limit residency.

Check your reasoning

Registers are logically thread-private and allocated from finite SM/SMSP capacity; a warp is assigned to a scheduler; shared memory is block-scoped and allocated from the SM carveout; L1/shared capacity is SM-wide; Tensor Core instructions issue through SM execution resources; L2 and HBM are device-wide. Registers, shared memory, threads, blocks, and architectural limits can constrain residency.

Review cue. When a kernel underperforms, ask separately whether it lacks eligible warps, waits on data, saturates a pipeline, or loses residency to resource pressure.

4. Read the grid, block, warp, and SM hierarchy

Outcome. Explain how logical CUDA work is scheduled onto H100 SMs and connect that hierarchy to PyTorch kernels.
Recall first. Which unit stays on one SM for its lifetime: a grid, a thread block, a warp, or an entire PyTorch model?

A kernel launch creates a grid of thread blocks. A block is assigned to one streaming multiprocessor and does not migrate or split across SMs. Hardware groups block threads into warps of 32 threads. Warp schedulers choose eligible warps and issue instructions to execution pipelines. The same high-level PyTorch operator may launch one optimized library kernel, several kernels, or a compiled fused kernel.

Threads provide logical parallelism; blocks provide scheduling and shared-memory scope; warps are the instruction-issue group; SMs own schedulers, registers, shared memory/L1, and execution pipelines. Tensor Cores are specialized matrix units reached by eligible instructions inside suitable kernels. They are not a separate place where a tensor is stored.

Kernel names and counts are implementation details that can change with shape, dtype, PyTorch/CUDA version, and compiler decisions. Profile them to understand a measured environment; do not make a course contract depend on a vendor-internal kernel name.

CUDA and Triton expose related but different launch abstractions. A CUDA grid contains thread blocks, and each block declares physical CUDA threads. A Triton grid contains program instances; a kernel meta-parameter such as BLOCK_SIZE commonly declares how many tensor elements one program covers, while num_warps controls the program's physical warp team. Therefore programs × BLOCK_SIZE counts covered element lanes, not CUDA threads. A one-dimensional element offset is commonly program_id × BLOCK_SIZE + lane, and the final program needs a bounds mask.

CUDA threads per block and Triton elements/warps per program are separate measured choices. They can change residency, register/shared-memory pressure, occupancy, and tail waste, but a hardware limit is not a universal optimum. High-level PyTorch normally chooses library or compiler-generated geometry; a custom Triton or CUDA kernel is justified only after profiles show that library operations, layout changes, and compilation do not express the required work efficiently.

Worked example

A PyTorch sequence containing matrix multiplication, layer normalization, bias addition, GELU, squaring, and reduction expresses six conceptual steps. The profiler may show library calls and multiple CUDA events. That observation links the Python program to launched work. It does not reveal block dimensions or instruction mix; those require a kernel profiler.

Practice

Run Lab 08. For each of the top CUDA events, map it to the most plausible high-level operation. Then classify each mapping as “confirmed by name,” “inferred from order/shape,” or “unknown.” Why is “unknown” a valid answer?

Check your reasoning

The block is the scheduling and shared-memory unit that remains on one SM. Kernel/event names may make matrix and reduction work recognizable, but fused or generic names can hide provenance. “Unknown” prevents an unsupported claim; use shapes, NVTX ranges, or a smaller controlled workload to disambiguate.

Review cue. Return to this hierarchy when a profiler reports low occupancy, divergence, many launches, or Tensor Core ineligibility.

5. Follow a PyTorch call to completed CUDA work

Outcome. Distinguish Python dispatch, kernel enqueue, stream ordering, device execution, and completion.
Recall first. If a Python call returns before its CUDA kernel finishes, what did a surrounding host timer actually measure?

A PyTorch expression first runs Python and dispatcher logic on the CPU. The selected CUDA implementation prepares arguments and enqueues kernels or copies onto a CUDA stream. Enqueueing is ordered within a stream, but the host normally continues without waiting for device completion. An error may surface only at a later synchronization point.

The default stream is not “the GPU”; it is one ordered work queue. Additional streams can expose independent copy or compute work, but concurrency occurs only when dependencies and hardware resources permit it. A tensor produced on one stream must not be consumed on another until the consumer waits for the producer. PyTorch records many dependencies automatically, yet custom stream code must keep tensor lifetimes and ordering correct.

Use host wall time for end-to-end application intervals that intentionally include completion. Use CUDA events for device intervals on streams. A call to torch.cuda.synchronize() makes a host timer honest, but synchronizing inside a production loop can destroy overlap; place it at the measurement boundary.

Worked example

The CPU enqueues two matrix multiplications in a fraction of the time the device needs to finish them. A naive host timer reports only enqueue overhead. Recording a CUDA event before and after the work, then synchronizing the end event, measures the device interval. Putting independent multiplications on two streams may or may not shorten the interval because each GEMM can already occupy most execution resources.

Practice

  1. Run Lab 07 and compare host enqueue median with device median.
  2. Explain why a lack of stream speedup does not disprove asynchrony.
  3. Name the event or wait needed when stream B consumes stream A's result.
Check your reasoning

Host enqueue time can be far smaller than completed device time. Two streams prove independent scheduling, not guaranteed overlap or improvement; saturated kernels may serialize on resources. A cross-stream consumer must wait on the producing stream or an event recorded after production. Synchronizing the entire device is correct but broader than necessary.

Review cue. Before interpreting any later timing, label it host, device, or end-to-end and mark the completion boundary.

6. Build a trustworthy two-node baseline

Outcome. Define a measurement that another learner can reproduce and know when the result is invalid.
Recall first. What information is missing from the statement “the GPU step took 4 ms”? Name at least five fields.

A benchmark is a controlled comparison, not a stopwatch reading. Freeze the operation, input shapes, dtypes, data placement, warm-up, number of samples, correctness rule, and primary metric before the first run. Keep scheduler job IDs, hostnames, and exact fabric details only in the private evidence package. The shareable summary uses the random course run ID plus node count, GPU family, MIG status, driver, CUDA runtime reported by PyTorch, PyTorch version, NCCL version when used, and a sanitized topology class. A later result is comparable only when the fields relevant to the hypothesis match.

Warm-up separates one-time work—CUDA context creation, library loading, allocator growth, algorithm selection, and compilation—from steady-state work. Keep first-call cost when it matters to the user, but label it separately. Preserve every timed sample; the median describes the center and a tail percentile exposes instability that a best time hides.

Correctness is part of performance. Exact copies and collective invariants can use exact checks. Reduced-precision math needs a tolerance chosen before measurement. Training needs finite loss and gradients plus an agreed quality or convergence check. A faster result that violates the gate is rejected.

7. Map a slow result to the system’s critical path

Outcome. Name the main limiter families and choose evidence that distinguishes one from another.
Recall first. Why can low HBM throughput mean either “the kernel does little memory work” or “the GPU is idle,” rather than proving a memory bottleneck?

A bottleneck is the resource or dependency that constrains the metric you care about at the current workload. The first step is therefore to define the metric and its boundary. Kernel latency, training-step time, request latency, and cluster throughput can have different critical paths even when they execute the same operator.

Use a timeline before a counter. Long CPU gaps suggest launch overhead, input starvation, blocking synchronization, or another host dependency. Long copies on the critical path suggest transfer work. Long, continuously executing kernels require kernel-level evidence: useful memory traffic, cache behavior, arithmetic throughput, instruction dependencies, divergence, and available parallelism. Distributed gaps add collective and fabric dependencies. Capacity is slightly different: it may prevent the desired batch or model from running even when it is not the slowest interval.

A utilization percentage is an observation, not a cause. High “GPU utilization” can include inefficient kernels; low utilization can result from short bursts separated by host work. For each first hypothesis, name one corroborating measurement and one disconfirming control. The smallest useful experiment changes one causal factor while keeping the workload and correctness contract fixed.

Worked example

A trace shows a 20 ms training step with 11 ms of CPU and data-loader gaps, 7 ms of kernels, and 2 ms of copies. Even if one kernel reaches high HBM throughput, kernel tuning cannot recover more than the kernel portion and is unlikely to be the first experiment. A ready-data control tests whether the gap belongs to the input path.

Practice

Choose a later lab and predict its likely limiter family before running it. Write one measurement that would support your prediction and one result that would redirect you to a different family.

Check your reasoning

A useful answer connects the metric boundary, visible timeline interval, candidate subsystem, and a disconfirming control. “GPU utilization is low” is incomplete because it does not identify why useful GPU work is absent.

8. Separate latency hiding, occupancy, and utilization

Outcome. Reason about resident warps and divergence without treating maximum occupancy as the goal.
Recall first. Can a kernel with lower occupancy be faster than one with higher occupancy? Give one reason.

When a warp waits for data or a dependency, an SM can issue an eligible instruction from another resident warp. Occupancy describes how many warps or blocks are resident relative to an architectural limit. Registers per thread, shared memory per block, threads per block, and hardware limits determine how many blocks can reside together. Hopper H100 keeps up to 64 concurrent warps per SM, has 64K 32-bit registers per SM, and supports up to 32 blocks per SM; exact residency still depends on the kernel.

More occupancy can improve latency hiding until enough independent work is available. After that point, forcing lower register use or smaller shared-memory tiles may make each warp do more work or generate extra memory traffic. The target is the fastest correct kernel, not an occupancy percentage.

Warp divergence occurs when threads in one warp follow different control paths. The warp must make progress through the required paths while masking threads that are inactive for each path. Short predicated choices can be cheap; long imbalanced branches can waste issue opportunities. Divergence between different warps is not the same problem.

Utilization is broader: a sampled busy percentage can be high while the wrong unit is saturated, and low while short bursts complete the required work. Always pair utilization with a workload timeline and specific kernel evidence.

Worked example

Kernel A uses many registers and reaches 50% theoretical occupancy but keeps data in registers. Kernel B is changed to use fewer registers and reaches 100% occupancy, yet spills values to device memory. Kernel B can be slower because extra memory traffic costs more than the added resident warps save. The experiment must compare time and spill/memory evidence, not occupancy alone.

Practice

Classify each statement as valid or invalid: (a) “GPU utilization is 95%, so the kernel is compute-bound”; (b) “occupancy rose, therefore latency fell”; (c) “a warp branch with equal work on both paths can cost more than uniform control”; (d) “register spills can trade occupancy for memory traffic.”

Check your reasoning

(a) Invalid: busy time does not identify the limiting unit. (b) Invalid without timing and resource evidence. (c) Valid: divergent paths can be serialized for the warp. (d) Valid: spills are backed by device memory and may outweigh residency gains.

Review cue. When Nsight reports occupancy, write the resource limiter beside it and ask what latency is being hidden.

Part III · Data movement and computation

9. Trace bytes through the memory hierarchy

Outcome. Identify where tensors, caches, shared tiles, registers, and allocator reservations live and which movement can dominate.
Recall first. What is the difference between PyTorch memory that is allocated to live tensors and memory reserved by its caching allocator?

Host memory sits outside the GPU and normally crosses PCIe in this course environment. HBM holds the large device working set. L2 is shared by SMs. Each SM combines configurable shared memory and L1/texture caching, while registers hold per-thread values closest to execution. Capacity generally grows as data moves outward; latency and explicit control change at every level.

PyTorch's caching allocator requests larger blocks from CUDA, serves tensor allocations from them, and keeps freed blocks for reuse. memory_allocated() reports bytes occupied by tensors; memory_reserved() reports the allocator's managed pool. Memory visible in nvidia-smi can therefore remain high after tensors are freed. empty_cache() releases unused cached blocks to other applications but cannot free live tensors and is not a routine performance optimization.

Registers and shared memory are kernel resources, not PyTorch tensor placement choices. A high-level user influences them indirectly through selected operators, shapes, dtypes, compilation, and libraries. Register spilling creates local-memory traffic backed by device memory. Shared-memory tiling can turn repeated HBM reads into on-chip reuse, but large tiles may reduce resident blocks.

Hopper adds advanced kernel mechanisms at this boundary. The Tensor Memory Accelerator (TMA) can move multidimensional tiles between global and shared memory while reducing address-generation work by CUDA threads. Distributed shared memory lets blocks in a thread-block cluster address one another's shared-memory regions. Both mechanisms require compatible CUDA kernels or libraries, synchronization, and measured reuse; neither is a place where a PyTorch user can directly move a tensor. They are extension topics, not prerequisites for this course's operator-level labs.

Worked example

A 1 GiB tensor is deleted. Allocated bytes fall, but reserved bytes stay nearly unchanged because the allocator retains the block. A later similar tensor can reuse it without another device allocation. Calling empty_cache() would make more memory visible to another process but can add allocation work when the current process needs the space again.

Practice

Draw the path for a batch that starts in pageable host memory, is copied to a CUDA tensor, used by a matrix kernel, and reduced to a scalar read by Python. Label which boundaries are explicit in PyTorch and which storage levels are managed inside the kernel/hardware.

Check your reasoning

The explicit application path is pageable host memory → possibly pinned staging → PCIe → HBM allocation → kernels → HBM result → host scalar when read. L2, L1/shared memory, and registers are on the device path but are selected by hardware and kernel implementation rather than by moving a PyTorch tensor to a named cache.

Review cue. Before treating an OOM or high memory reading as a capacity fact, separate live tensors, reserved pool, temporary workspaces, and other processes.

10. Connect tensor layout to useful memory transactions

Outcome. Use shapes, strides, contiguity, and reuse to decide whether repacking can pay for itself.
Recall first. Why can a tensor view have the same values and shape as another tensor but very different access cost?

A tensor's shape describes logical indices; strides describe how those indices map to storage. Threads in a warp are most efficient when their addresses combine into a small number of aligned memory transactions. A contiguous elementwise traversal usually supports this. A large stride can fetch segments containing few useful bytes, reducing effective bandwidth.

Views such as transpose often change strides without moving data. Some operators can consume noncontiguous layouts directly; others make an implicit copy or select a different kernel. Calling contiguous() creates an explicit copy when required. The copy is an optimization only if later work reuses the packed layout enough to repay it.

Measure three branches: direct use of the view, pack plus one use, and pack plus repeated reuse. Report the copy time. Compare equivalent results, and keep the same logical work. Effective bandwidth based only on useful bytes can reveal wasted transactions but must not be mistaken for raw HBM traffic.

Worked example

A transposed matrix is used once by an operation that already supports its stride. Explicit repacking adds a full copy and is unlikely to win. The same view is reused in 100 iterations by a kernel that accesses it poorly; one copy may be amortized. The break-even reuse count is the smallest count where copy + packed uses is faster than direct strided uses.

Practice

Run Lab 04 and inspect stride() and is_contiguous() for every case. Compute a measured break-even reuse count. Explain why that number belongs to the recorded environment and shape, not to “transposes” in general.

Check your reasoning

The correct decision includes the packing cost and equivalent downstream work. The break-even point changes with shape, cache behavior, consuming operator, dtype, implementation, and GPU. A view is not slow merely because it is noncontiguous; the consuming access pattern decides.

Review cue. When a profiler shows memory pressure, inspect tensor strides and implicit copies before changing arithmetic.

11. Move data deliberately and prove overlap

Outcome. Choose pageable or pinned memory, blocking or non-blocking copies, and streams based on measured pipeline behavior.
Recall first. Why does non_blocking=True not by itself prove that a host-to-device copy overlapped computation?

DMA engines can transfer pinned host pages directly; pageable pages generally require staging. PyTorch data loaders can produce pinned batches, and non_blocking=True can let the host enqueue an asynchronous copy when the source and context support it. Pinning consumes a limited host resource, so pin the batches that feed the GPU rather than an unbounded dataset.

Overlap needs four things: a copy capable of asynchronous execution, a separate stream when appropriate, independent compute, and hardware resources that can progress both. It also needs correct dependencies. A timeline is the evidence. Faster enqueue time is not overlap, and a non-blocking call followed immediately by a full synchronization cannot hide useful work.

Double buffering is a common pattern: while compute consumes device batch N, a copy stream prepares device batch N+1. An event tells the compute stream when N+1 is ready. Host data must remain alive until the asynchronous copy finishes. Start with correctness and a two-stage timeline before adding more buffers.

Worked example

A blocking loop performs copy(N), wait, compute(N), wait. A pipelined loop preloads batch 0, then overlaps copy(N+1) with compute(N), joining only before the consumer needs N+1. If both copy and compute take 4 ms and overlap perfectly, a long pipeline approaches about 4 ms per batch after fill—not 8 ms—but real kernels and PCIe engines may contend or fail to overlap.

Practice

Run Lab 03 for pageable/pinned and blocking/non-blocking modes, then Lab 07 for stream behavior. Write a proposed two-buffer dependency graph. Name the producer event, consumer wait, and lifetime requirement for each host buffer.

Check your reasoning

Pinned, non-blocking copies enable the intended pipeline, but only a trace or end-to-end remeasurement proves benefit. Each host buffer must not be modified or freed until its copy completes. The compute stream waits for the ready event of the device buffer it consumes; the copy stream must not overwrite a device buffer still in use.

Review cue. Whenever “overlap” appears in a recommendation, demand a timeline that shows simultaneous useful intervals and preserved dependencies.

12. Choose precision and Tensor Core paths intentionally

Outcome. Relate FP32, TF32, BF16, FP16, and FP8 to range, storage, eligible operations, and correctness.
Recall first. Which statement is safer: “BF16 uses Tensor Cores” or “an eligible BF16 matrix operation can use a Tensor Core kernel”? Why?

FP32, BF16, FP16, and FP8 describe stored numeric formats. TF32 is an NVIDIA Tensor Core math mode for eligible FP32 matrix operations: it preserves FP32 range at the interface while using reduced mantissa precision internally. BF16 has a wide exponent range and fewer fraction bits; FP16 has more fraction bits but a narrower range. Accumulation may use wider precision than inputs.

Tensor Cores did not begin with Hopper: NVIDIA introduced them with Volta. Hopper provides fourth-generation Tensor Cores plus Transformer Engine support for FP8 workflows. Tensor Cores execute supported matrix-oriented instructions, and dtype alone is not enough: operation type, dimensions, alignment, layout, library/kernel selection, and workload size determine the path. H100 supports FP8 Tensor Core operation through appropriate libraries and scale management. H100 is not a Blackwell NVFP4 device; do not transfer FP4 claims across architectures.

Correctness duties grow as precision narrows. Compare to a defined reference, inspect maximum and distributional error, check finite outputs, and for training verify gradients, loss behavior, convergence, and downstream quality. A microbenchmark can prove kernel behavior but not model quality.

13. Use roofline thinking to choose the next experiment

Outcome. Classify low arithmetic intensity, compute ceilings, and below-roof inefficiency without treating theoretical peaks as promises.
Recall first. A vector add and a large matrix multiply move data and perform math. Which usually has higher useful operations per byte, and why?

Arithmetic intensity is useful operations divided by bytes transferred across the memory boundary being studied. A vector expression performs few operations per element and often approaches a memory-bandwidth roof. Matrix multiplication reuses each input across many multiply-accumulate operations and can reach much higher intensity. The ridge point is where the sloped bandwidth roof meets the flat compute roof.

The simple roofline is a classifier. Below the sloped roof, reduce bytes, improve layout, or increase reuse. Near the compute roof, improve eligible math throughput, shape, or instruction mix. Far below both roofs, suspect launch gaps, synchronization, insufficient parallel work, dependencies, or another subsystem. Cache behavior means the relevant byte count may be HBM, L2, or a higher level; state which one the estimate uses.

Do not divide by marketing peak and call the remainder “optimization opportunity.” Peaks depend on format and conditions, while real kernels perform instructions and transfers not counted as useful work. Use measured bandwidth and achieved work rate from a controlled lab, then profile the responsible kernel when the next decision requires it.

Worked example

A vector add reads two arrays and writes one: roughly three element transfers for one addition. A large GEMM reuses rows and columns so useful operations grow roughly with the cube of width while input/output elements grow with the square. This is why the operations occupy different roofline regions, even though both touch HBM.

14. Make two-node communication part of the workload

    samples = []

def break_even_reuses(
    copy_ms: float, strided_ms: float, packed_ms: float
) -> int | None:
    per_use_savings_ms = strided_ms - packed_ms
    if per_use_savings_ms <= 0:

    return max(1, math.ceil(copy_ms / per_use_savings_ms))

    operations = {
        "contiguous": lambda: torch.sin(contiguous) * 0.5 + contiguous,
        "strided_view": lambda: torch.sin(strided) * 0.5 + strided,
        "repacked_contiguous": lambda: torch.sin(packed) * 0.5 + packed,

"""Contrast host enqueue time, device time, and independent CUDA streams."""

from __future__ import annotations

import argparse
import statistics
import time

from common import (
    add_common_args,
    load_torch,
    require_h100,
    seed_everything,
    summarize_ms,
    validate_common_args,
    write_result,
)


def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser(description=__doc__)
    add_common_args(parser)
    return parser.parse_args()


def main() -> None:
    args = parse_args()
    validate_common_args(args)
    torch = load_torch()
    environment = require_h100(torch)
    seed_everything(torch, args.seed)
    width = 1_024 if args.profile == "smoke" else 4_096
    tensors = [
        torch.randn((width, width), device="cuda", dtype=torch.bfloat16)
        for _ in range(4)
    ]
    a, b, c, d = tensors
    stream_a = torch.cuda.Stream()
    stream_b = torch.cuda.Stream()

    def sequential() -> tuple[object, object]:
        return a @ b, c @ d

    def concurrent() -> tuple[object, object]:
        ready = torch.cuda.Event()
        ready.record()
        stream_a.wait_event(ready)
        stream_b.wait_event(ready)
        with torch.cuda.stream(stream_a):
            first = a @ b
        with torch.cuda.stream(stream_b):
            second = c @ d
        current = torch.cuda.current_stream()
        current.wait_stream(stream_a)
        current.wait_stream(stream_b)
        return first, second

    for _ in range(args.warmup):
        sequential()
        concurrent()
    torch.cuda.synchronize()

    host_enqueue_samples = []
    sequential_samples = []
    concurrent_samples = []
    sequential_result = None
    concurrent_result = None
    for _ in range(args.iterations):
        host_started = time.perf_counter()
        sequential_result = sequential()
        host_enqueue_samples.append((time.perf_counter() - host_started) * 1_000)
        torch.cuda.synchronize()

        start = torch.cuda.Event(enable_timing=True)
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        sequential_result = sequential()
        end.record()
        end.synchronize()
        sequential_samples.append(float(start.elapsed_time(end)))

        start = torch.cuda.Event(enable_timing=True)
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        concurrent_result = concurrent()
        end.record()
        end.synchronize()
        concurrent_samples.append(float(start.elapsed_time(end)))

    assert sequential_result is not None and concurrent_result is not None
    correct = all(
        torch.allclose(expected, observed, rtol=2e-2, atol=2e-2)
        for expected, observed in zip(sequential_result, concurrent_result, strict=True)
    )
    if not correct:
        raise SystemExit("Sequential and stream-based results diverged.")
    target = write_result(
        args,
        lab_id="07_async_streams",
        environment=environment,
        measurements={
            "matrix_width": width,
            "host_enqueue_median_ms": round(statistics.median(host_enqueue_samples), 4),
            "sequential_device": summarize_ms(sequential_samples),
            "independent_streams_device": summarize_ms(concurrent_samples),
        },
        correctness={"allclose": True},
    )
    print(f"Completed asynchronous stream experiment: {target}")

        source,

def cuda_times_ms(
    torch: Any,
    operation: Callable[[], Any],
    *,
    warmup: int,
    iterations: int,
) -> list[float]:
    for _ in range(warmup):
        operation()
    torch.cuda.synchronize()
    samples: list[float] = []
    for _ in range(iterations):
        start = torch.cuda.Event(enable_timing=True)
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        operation()
        end.record()
        end.synchronize()
        samples.append(float(start.elapsed_time(end)))
    return samples

def open_private_exclusive(target: Path, *, binary: bool = False) -> IO[Any]:
    target.parent.mkdir(mode=0o700, parents=True, exist_ok=True)
    flags = os.O_WRONLY | os.O_CREAT | os.O_EXCL
    try:
        descriptor = os.open(target, flags, 0o600)
    except FileExistsError as exc:
        raise SystemExit(
            f"Refusing to overwrite an existing artifact: {target}"
        ) from exc
    if binary:
        return os.fdopen(descriptor, "wb")
    return os.fdopen(descriptor, "w", encoding="utf-8")

    with open_private_exclusive(target) as stream:
        stream.write(document)
    return target
