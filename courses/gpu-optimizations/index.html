Part I · Performance foundations and evidence

1. See GPU performance as an end-to-end critical path

Outcome. Explain what can limit latency or throughput before choosing an optimization or a profiler.
Recall first. If a kernel becomes twice as fast but occupies only 10% of the application’s critical path, what is the largest end-to-end improvement it can provide?

GPU performance is the rate at which useful, correct work crosses a declared boundary. Latency measures time for one unit of work. Throughput measures completed work per unit time. They interact but are not interchangeable: batching can raise throughput while increasing the time one request waits. Begin with the user-visible objective and then trace the stages that contribute to it.

The critical path is the dependency chain that determines completion. Work off that path may consume resources without delaying the result; work on that path limits progress. In a simple pipeline, the stages include input preparation, CPU dispatch, host-to-device transfer, GPU kernels, synchronization, inter-rank communication, and output handling. Some stages can overlap, so elapsed time is not always their sum. The slowest exposed stage can change after every successful optimization.

Most slow GPU workloads fall into a small set of evidence families: host or launch overhead; input starvation; transfer or interconnect delay; memory-bandwidth or memory-latency pressure; compute-throughput pressure; insufficient parallelism, divergence, or wave tails; synchronization and serialization; and exposed communication. Memory capacity is a feasibility constraint that can force smaller batches, checkpointing, offload, or sharding and thereby create a new critical path.

Two simple models organize the investigation. Amdahl-style reasoning limits the end-to-end benefit of accelerating one fraction of the workload. Roofline reasoning compares useful operations per byte with measured memory and compute ceilings for a kernel. Neither model proves a cause; each tells you which measurement or control is worth running next.

Worked example

A 100 ms step spends 55 ms waiting for input, 10 ms dispatching, 30 ms in kernels, and 5 ms in synchronization. Even an idealized 2× speedup of every kernel saves only 15 ms. A ready-data control addresses the larger exposed interval and can reveal whether input preparation is the current limiter.

Practice

Check your reasoning

A strong answer separates measured time from inferred cause, accounts for overlap, and uses the original end-to-end metric. It does not select a technique merely because a GPU counter looks low or high.

2. Diagnose the five primary bottleneck classes

Outcome. Distinguish compute, memory-bandwidth, launch/CPU, communication, and input/storage bottlenecks, then separate them from cross-cutting mechanisms and capacity constraints.
Recall first. Why is “GPU utilization is high” insufficient to classify a workload as compute-bound?

A compute-bound kernel is limited by useful arithmetic throughput: eligible CUDA or Tensor Core pipelines remain busy, memory traffic is not the practical ceiling, and a faster eligible math path changes the result. A memory-bandwidth-bound kernel performs too little useful work for the bytes moved from HBM; reducing precision, fusing intermediates, or increasing reuse is more promising than adding arithmetic units.

A launch- or CPU-bound workload leaves gaps because Python, framework dispatch, scheduling, allocation, tokenization, or synchronization does not submit useful GPU work quickly enough. A communication-bound distributed workload exposes collectives or point-to-point transfers on the slowest rank's critical path. An input- or storage-bound workload waits for samples, preprocessing, checkpoints, model files, or host-to-device staging.

These five classes are the primary system-level starting point. Transfer serialization, poor layout, insufficient parallelism, divergence, synchronization, and rank imbalance are mechanisms that can create or amplify one of them; they are not always peer top-level classes. Capacity is a separate feasibility constraint: an out-of-memory workload must first be made runnable, after which its time bottleneck still needs measurement.

Every label remains a hypothesis until a disconfirming control moves the expected evidence. High GPU utilization alone cannot distinguish compute from memory traffic, and low utilization cannot distinguish host gaps from input starvation. Start with the complete critical path, then use a tool whose scope matches the uncertainty.

A training step shows a 40 ms blank GPU interval before each batch and then dense, efficient kernels. A ready device-resident batch removes 35 ms. That control supports an input/storage diagnosis; collecting Tensor Core counters first would have analyzed the healthy portion instead of the dominant exposed wait.

Practice

Check your reasoning

Strong answers map compute and memory questions to a selected-kernel report, launch/CPU and input questions to a timeline, and communication to rank-aware timelines plus substrate controls. Transfer is a mechanism on the data path, capacity is feasibility, and imbalance can expose communication or input waits.

Review cue. When an optimization succeeds, reprofile; the next-largest limiter may now dominate.

4. Connect PyTorch operators to CUDA work with NVTX

Outcome. Use a short PyTorch Profiler window and NVTX ranges to connect model phases, framework operators, CUDA kernels, copies, shapes, and allocations.
Recall first. What information does an NVTX range add, and why is it not a performance metric?

PyTorch Profiler is the first tool when the uncertainty is expressed in framework terms: which aten:: operation dominates, how many times it runs, which shapes it receives, whether copies or casts appear, or which operation allocates memory. It is included in the PyTorch installation. Select CPU and CUDA activities explicitly and keep the active window short because stack capture, shape recording, and memory profiling increase overhead and trace size.

NVTX adds semantic ranges to compatible timelines. Label phases such as forward, backward, optimizer, prefill, decode, or this course's profile_region. A range says what the application intended to do during an interval; it does not measure FLOPS, bandwidth, or efficiency. Keep labels at phase or block granularity so the timeline remains readable.

Use torch.profiler.schedule(wait=1, warmup=1, active=3, repeat=1) for a repeated loop, call profiler.step() once per iteration, and export one trace. In a small one-shot lab, a single bounded context is sufficient. Read the operator table by self CPU time, self CUDA time, call count, and shapes; then inspect copies and allocations before descending to the system timeline.

  --profile smoke --warmup 2 --iterations 5 --export-trace

5. Resolve system-level stalls with Nsight Systems

Outcome. Use an Nsight Systems timeline to diagnose GPU gaps, synchronization, launch pressure, transfer serialization, communication, and missing overlap.
Recall first. Why can Nsight Systems identify a memory copy on the critical path but not classify one kernel's arithmetic intensity?

Nsight Systems answers when work occurred and how CPU threads, CUDA APIs, kernels, copies, streams, NVTX ranges, and NCCL activity interact. Begin with it when the whole application is unfamiliar or the PyTorch trace suggests host gaps, copies, synchronization, or communication. Use a short representative run with CPU sampling disabled unless CPU call stacks are the question.

The supplied launcher records a .nsys-rep and generates a CLI statistics file. In the UI, start at the profile_region NVTX range. Check blank GPU intervals, CUDA API calls that block the host, kernel spacing and duration, memcpy direction and overlap, and whether ranks arrive at collectives together. The CLI summary is useful for kernel and API totals, but only the timeline shows dependency order and overlap.

Common practical patterns are deliberately available in Lab 14. The synchronization baseline calls .item() during each step; the optimized path keeps reductions on the GPU and reads once after the range. The launch baseline emits a storm of small pointwise kernels; the optimized path compiles the stable chain. These are teaching controls, not guaranteed production speedups.

6. Explain a kernel with Nsight Compute and roofline

Outcome. Interpret arithmetic intensity, effective TFLOP/s, compute/memory throughput, traffic, scheduler behavior, and occupancy for one selected kernel.
Recall first. What are the units of arithmetic intensity, and why is it different from bandwidth or FLOP/s?

Nsight Compute answers why one selected CUDA kernel uses the GPU as it does. Use it only after a framework or system trace identifies a stable, material kernel. Counter collection can replay the kernel, so profile one launch inside the profile_region NVTX range and use an unprofiled run for acceptance timing.

Arithmetic intensity (AI) is useful floating-point work divided by memory traffic, measured in FLOP per byte. It is not a rate. Effective workload TFLOP/s is the declared useful operation count divided by unprofiled elapsed seconds and then by 1012. That algorithmic value helps compare equivalent implementations; it is not automatically the same as hardware-issued instructions or a peak specification. Nsight Compute's roofline combines achieved work rate with AI and measured ceilings to show whether a kernel lies nearer a memory or compute boundary.

Section-set composition is version-dependent. Use ncu --list-sets and ncu --list-sections inside the allocation. Collect the verified roofline set for the roofline view, then add the verified MemoryWorkloadAnalysis, SchedulerStats, WarpStateStats, and Occupancy sections when the exercise requires them. Speed of Light summarizes achieved compute and memory throughput relative to the device. Memory Workload Analysis separates DRAM, L2, L1/texture, shared-memory traffic, sectors, and cache behavior. Scheduler and Warp State sections show whether eligible warps issue and why they wait. Occupancy identifies residency limits, but high occupancy is neither necessary nor sufficient for high performance.

7. Choose monitoring and benchmark tools by scope

Outcome. Choose nvidia-smi, DCGM, nvbandwidth, NCCL Tests, framework-level distributed evidence, vLLM Bench, AIPerf, or MLPerf for the question each tool can answer, without treating telemetry or client metrics as kernel diagnosis.
Recall first. If DCGM reports high SM activity during a slow request, what important causes remain unresolved?

nvidia-smi is a snapshot and coarse sampler for visibility, allocation, memory use, clocks, power, temperature, and device activity. It can reveal an idle GPU, unexpected process, memory pressure, or throttling candidate, but “GPU utilization” only means kernels were active during part of a sampling window. It does not state whether those kernels used memory or compute efficiently.

DCGM provides continuous health, topology, job, and interval telemetry. DCGM Exporter exposes a selected field set in Prometheus format for fleet or job-correlated monitoring; exporter deployment, labels, endpoint protection, and retention belong to the cluster operator. Neither DCGM nor its exporter identifies a PyTorch operator or source line. Discover supported profiling fields on the actual H100 before choosing IDs, then correlate timestamped activity with the course's random run identifier. Raw discovery and exporter data remains private because it can expose device, workload, or topology identifiers. DCGM hardware-counter watches can conflict with Nsight tools; pause/resume is host-engine-wide and must be coordinated by the site owner.

Part III · Measurement and targeted optimization

8. Turn “make it faster” into a falsifiable experiment

Outcome. Freeze a user-visible objective, equivalent workload, correctness gate, and acceptance rule.
Recall first. Why are kernel latency, training tokens per second, and serving p90 latency not interchangeable optimization targets?

Optimization begins with the outcome a user experiences. Name the workload boundary: one kernel, one model step, an epoch, one request, or a concurrency window. Choose one primary metric and keep secondary metrics for explanation. Freeze inputs, shapes, dtypes, batch semantics, random seed, warm-up, sample count, rank count, and software environment.

Define equivalence before changing code. Pointwise kernels may require numerical tolerance; training variants need the same effective global tokens and an agreed loss or quality rule; serving variants need the same prompt/output distribution and decoding settings. Memory-saving techniques that reduce batch size or recompute work must still answer the original objective.

Stability is part of equivalence. Record GPU clocks or throttling evidence, power limit, temperature, CPU and NUMA placement, storage/cache state, background load, and whether another job shares the node or fabric. You do not need to eliminate all variance, but you must keep known controls constant, randomize or alternate branch order when drift is possible, and report a distribution rather than one favorable sample.

Write the acceptance rule in advance: for example, “median step time improves and p90 does not regress beyond the declared bound; gradients remain within tolerance; peak memory stays below the budget.” Keep the baseline executable and preserve raw samples. Compilation, autotuning, and allocator growth belong either in a separately measured startup objective or outside the warmed steady-state interval.

Worked example

A compiled branch reports 20% lower warmed kernel time but its first call adds 40 seconds. For a week-long training job, warmed throughput may dominate. For an infrequently invoked service that cold-starts per request, first-call cost may reject the change. The same implementation can therefore pass one contract and fail another.

Practice

Write contracts for (a) a training throughput experiment and (b) a low-concurrency inference experiment. Each must specify boundary, metric, correctness/quality, memory limit, warm-up, samples, and the two-node scaling semantics.

Check your reasoning

Training commonly uses global tokens per second with fixed global batch/sequence and finite loss/gradient or validation checks. 9. Time asynchronous CUDA work correctly

Outcome. Choose host timers, CUDA events, profiler intervals, and synchronization boundaries that match the question.
Recall first. What does a host timer around an asynchronous PyTorch CUDA call measure when no completion boundary follows?

For a device interval, record CUDA events on the relevant stream and synchronize the end event. For end-to-end latency, use a host timer that includes the intended completion point.

Record a distribution after warm-up; one best time hides contention and variance. Synchronization is a measurement tool, not a default application pattern. Placing torch.cuda.synchronize() between every operation changes the schedule and can remove natural overlap.

10. Repair launch- and CPU-bound execution

Outcome. Reduce Python gaps, graph breaks, tiny launches, and accidental synchronization without hiding dynamic requirements.
Recall first. Name two reasons a workload can contain many short CUDA kernels even when each kernel is individually efficient.

Launch-bound workloads do too little device work per host decision. Common causes are tiny batches, Python loops over tensor operations, scalar reads such as .item(), data-dependent control, repeated allocation, graph breaks, and many pointwise intermediates. The system timeline—not an isolated kernel profile—shows the gaps.

Measure compilation separately and inspect recompilation or break diagnostics. CUDA Graphs replay a fixed sequence with stable memory addresses, reducing CPU launch overhead at the cost of dynamic flexibility and capture constraints.

Choose the least restrictive technique. Batching changes latency and memory. Compilation preserves more dynamism but may break or recompile. CUDA Graphs require static-enough shapes, storage, and capture-safe operations. A fast smoke run does not justify graphing a workload whose production shapes change every request.

11. Repair transfer-bound pipelines and prove overlap

Recall first. What evidence distinguishes faster host enqueue from actual copy/compute overlap?

Then improve necessary transfers with pinned source memory and non-blocking copies. Finally pipeline only when the copy and compute are independent.

13. Balance launch geometry, parallelism, divergence, and SM resources

Outcome. Explain why a kernel can be below both memory and compute ceilings and test the responsible execution constraint.
Recall first. Why can raising occupancy make a kernel slower when it increases register spills or reduces useful work per block?

A kernel needs enough independent work to keep many SMs and their schedulers useful. The grid supplies thread blocks; blocks arrive in waves when there are more blocks than can reside across the GPU at once. A small grid can leave SMs unused. A final partial wave creates a tail. Very small blocks may provide too few warps per block, while very large blocks can consume resources that reduce concurrent residency.

Residency is constrained jointly by threads, blocks, registers, shared memory, and architectural limits. Occupancy is the fraction of the maximum resident warps that are present, not the fraction of useful peak performance. More resident warps can hide memory or dependency latency, but extra occupancy does not help when the kernel already has enough eligible work or when another pipeline is saturated. Always pair occupancy with eligible-warps, stall, throughput, and elapsed-time evidence.

Control flow and memory behavior can waste work within a warp. Divergent branches make different lane paths execute under masks, so not every lane performs useful work each instruction. Strided global accesses can require extra memory sectors. Shared-memory bank conflicts serialize accesses that could otherwise proceed together. High register demand can reduce residency; forcing the demand down can create spills to local memory, which is backed by device memory. These mechanisms need different fixes even when they all reduce throughput.

Start with a block-size or tile-size sweep over representative shapes. Record correctness, elapsed time, grid size, waves, registers per thread, shared memory per block, achieved occupancy, eligible warps, and relevant memory or pipeline metrics. Keep the fastest correct configuration for the workload distribution, not the configuration with the largest occupancy number.

Worked example

A block-size change raises occupancy from 50% to 75% but increases local-memory traffic because the compiler spills registers. The higher-occupancy branch is slower. A different tile size reduces the number of blocks to fewer than the available SMs, creating a one-wave underfill. Neither result can be understood from occupancy alone.

15. Distinguish fusion, compilation, and CUDA Graph replay

Outcome. Choose compilation or graphing based on the workload's dynamism and measured overhead.
Recall first. Which technique primarily changes kernel generation, and which primarily changes repeated launch submission?

torch.compile captures a PyTorch graph and can generate fused or specialized kernels. It may spend significant time tracing and compiling, and graph breaks or guard failures can create multiple compiled variants. CUDA Graphs capture a sequence of already selected CUDA work and replay it with fixed virtual addresses, dramatically reducing repeated launch overhead while constraining dynamic behavior.

The techniques can compose, but measure them separately first. Warm compilation, warm graph capture, and steady replay are different phases. Graph-private memory pools can increase reserved memory. Captured inputs must use stable addresses, and unsafe allocation or synchronization during capture can fail or corrupt assumptions.

Use compilation for operator fusion and generated-kernel improvement; use graphs when the remaining bottleneck is CPU submission for a stable schedule. Reject either when startup, recompilation, memory, or dynamism violates the contract.

Escalate to a custom CUDA or Triton kernel only after the profiler isolates an important operation that library selection, layout, shape, batching, and compilation do not repair. A custom kernel owns indexing, masking, launch geometry, resource use, numerical tests, and maintenance across versions. Preserve an eager or library reference and benchmark representative shapes. 17. Recover memory capacity through recomputation, state reduction, and fragmentation control

Outcome. Use memory ledgers, activation checkpointing, accumulation, and allocator evidence to fit the intended workload.
Recall first. Which memory entry does activation checkpointing reduce, and what does it spend instead?

Capacity limits differ from bandwidth limits. First classify live parameters, gradients, optimizer state, activations, temporary workspaces, communication buffers, and allocator reservation. Peak allocation—not the model file alone—decides whether the target step fits.

Activation checkpointing saves selected intermediates and recomputes them during backward, reducing activation memory while increasing compute. Gradient accumulation reduces microbatch activation peak while preserving a larger effective batch across multiple microsteps. Sharding reduces persistent state but adds communication. These techniques act on different ledger entries and can compose.

Fragmentation or reserved unused blocks can make allocator behavior confusing. Use PyTorch allocation/reservation statistics and memory snapshots where needed. empty_cache() cannot free live tensors and is not a substitute for fixing a workload whose peak genuinely exceeds capacity.

PyTorch's CUDA caching allocator distinguishes live tensor bytes from reserved segments retained for reuse. Deleting a tensor can reduce allocated bytes while reserved bytes stay high. A reserved-minus-allocated gap is not automatically a leak: it can be reusable cached space, inactive split blocks, or fragmentation. empty_cache() releases eligible unused cache to the driver but cannot free live tensors and does not lower the memory required by the same live workload.

Worked example

A model's persistent state uses 30 GiB and activations peak at 55 GiB, exceeding an 80 GiB H100 after workspaces. Checkpointing halves saved activations but adds recomputation, allowing the target sequence. If optimizer state instead dominates, checkpointing may not solve the OOM; sharding or optimizer changes address a different ledger entry.

    class SyntheticDataset(torch.utils.data.Dataset):

            return (batches + args.warmup) * 8

            sample = torch.randn(feature_width, generator=generator)

            dataset,

            pin_memory=True,

            "batch_ready_gap": [],
            "h2d": [],
            "device_consumption": [],
            "end_to_end": [],

        },

    )

"""Measure the memory/time tradeoff from activation checkpointing."""

from __future__ import annotations

import argparse
import math
import statistics
import time

from common import (
    add_common_args,
    load_torch,
    require_h100,
    seed_everything,
    validate_common_args,
    write_result,
)


def main() -> None:
    parser = argparse.ArgumentParser(description=__doc__)
    add_common_args(parser)
    args = parser.parse_args()
    validate_common_args(args)
    torch = load_torch()
    environment = require_h100(torch)
    seed_everything(torch, args.seed)
    from torch.utils.checkpoint import checkpoint

    def run_layers(layer_set: object, inputs: object, use_checkpoint: bool) -> object:
        hidden = inputs
        for layer in layer_set:

            def function(value: object, layer: object = layer) -> object:
                return torch.nn.functional.gelu(layer(value))

            hidden = (
                checkpoint(function, hidden, use_reentrant=False)
                if use_checkpoint
                else function(hidden)
            )
        return hidden

    probe_width = 512
    probe_depth = 2
    probe_batch = 4
    probe_layers = torch.nn.ModuleList(
        [
            torch.nn.Linear(
                probe_width,
                probe_width,
                bias=False,
                device="cuda",
                dtype=torch.bfloat16,
            )
            for _ in range(probe_depth)
        ]
    )
    probe_inputs = torch.randn(
        (probe_batch, probe_width), device="cuda", dtype=torch.bfloat16
    )

    def gradient_snapshot(
        use_checkpoint: bool,
    ) -> tuple[float, list[tuple[str, object]]]:
        probe_layers.zero_grad(set_to_none=True)
        inputs = probe_inputs.detach().clone().requires_grad_(True)
        hidden = run_layers(probe_layers, inputs, use_checkpoint)
        loss = hidden.float().square().mean()
        loss.backward()
        gradients = [("inputs", inputs.grad)]
        gradients.extend(
            (f"layer_{index}.weight", layer.weight.grad)
            for index, layer in enumerate(probe_layers)
        )
        if any(gradient is None for _, gradient in gradients):
            raise SystemExit("The checkpointing probe produced a missing gradient.")
        if any(
            not bool(torch.isfinite(gradient).all().item()) for _, gradient in gradients
        ):
            raise SystemExit("The checkpointing probe produced a non-finite gradient.")
        return float(loss.detach()), [
            (name, gradient.detach().float().cpu().clone())
            for name, gradient in gradients
        ]

    baseline_probe_loss, baseline_gradients = gradient_snapshot(False)
    checkpoint_probe_loss, checkpoint_gradients = gradient_snapshot(True)
    if [name for name, _ in baseline_gradients] != [
        name for name, _ in checkpoint_gradients
    ]:
        raise SystemExit("Checkpointing probe gradient names diverged.")
    gradients_allclose = True
    max_abs_gradient_error = 0.0
    squared_gradient_error = 0.0
    squared_reference_norm = 0.0
    for (name, baseline_gradient), (other_name, checkpoint_gradient) in zip(
        baseline_gradients, checkpoint_gradients, strict=True
    ):
        if name != other_name:
            raise SystemExit("Checkpointing probe gradient order diverged.")
        difference = checkpoint_gradient - baseline_gradient
        max_abs_gradient_error = max(
            max_abs_gradient_error, float(difference.abs().max().item())
        )
        squared_gradient_error += float(difference.square().sum().item())
        squared_reference_norm += float(baseline_gradient.square().sum().item())
        gradients_allclose = gradients_allclose and bool(
            torch.allclose(
                baseline_gradient,
                checkpoint_gradient,
                rtol=5e-2,
                atol=5e-2,
            )
        )
    relative_l2_gradient_error = math.sqrt(squared_gradient_error) / max(
        math.sqrt(squared_reference_norm), 1e-12
    )
    probe_loss_close = math.isclose(
        baseline_probe_loss, checkpoint_probe_loss, rel_tol=5e-2, abs_tol=5e-2
    )
    if not gradients_allclose or not probe_loss_close:
        raise SystemExit("Checkpointed and eager correctness-probe results diverged.")
    probe_layers.to("cpu")
    probe_inputs = probe_inputs.cpu()
    baseline_gradients.clear()
    checkpoint_gradients.clear()
    torch.cuda.empty_cache()

    width = 2_048 if args.profile == "smoke" else 8_192
    depth = 4 if args.profile == "smoke" else 8
    batch = 16
    layers = torch.nn.ModuleList(
        [
            torch.nn.Linear(
                width, width, bias=False, device="cuda", dtype=torch.bfloat16
            )
            for _ in range(depth)
        ]
    )
    base_inputs = torch.randn((batch, width), device="cuda", dtype=torch.bfloat16)

    def train_step(use_checkpoint: bool) -> float:
        layers.zero_grad(set_to_none=True)
        inputs = base_inputs.detach().clone().requires_grad_(True)
        hidden = run_layers(layers, inputs, use_checkpoint)
        loss = hidden.float().square().mean()
        loss.backward()
        return float(loss.detach())

    rows = {}
    losses = {}
    for label, enabled in (("baseline", False), ("checkpointed", True)):
        samples = []
        peaks = []
        for _ in range(args.warmup):
            train_step(enabled)
        torch.cuda.synchronize()
        for _ in range(args.iterations):
            torch.cuda.reset_peak_memory_stats()
            start = time.perf_counter()
            losses[label] = train_step(enabled)
            torch.cuda.synchronize()
            samples.append((time.perf_counter() - start) * 1_000)
            peaks.append(torch.cuda.max_memory_allocated() / 2**20)
        rows[label] = {
            "median_ms": round(statistics.median(samples), 4),
            "peak_allocated_mib": round(statistics.median(peaks), 2),
        }
    correct = abs(losses["baseline"] - losses["checkpointed"]) <= 1e-2
    if not correct:
        raise SystemExit("Checkpointed and baseline loss values diverged unexpectedly.")
    target = write_result(
        args,
        lab_id="06_activation_checkpointing",
        environment=environment,
        measurements={
            "width": width,
            "depth": depth,
            "variants": rows,
            "correctness_probe": {
                "shape": {
                    "batch": probe_batch,
                    "width": probe_width,
                    "depth": probe_depth,
                },
                "rtol": 5e-2,
                "atol": 5e-2,
                "max_abs_gradient_error": round(max_abs_gradient_error, 8),
                "relative_l2_gradient_error": round(relative_l2_gradient_error, 8),
            },
        },
        correctness={
            "loss_close": True,
            "probe_loss_close": True,
            "gradients_allclose": True,
        },
    )
    print(f"Completed checkpointing experiment: {target}")

        communication_stream.wait_stream(default_stream)

from __future__ import annotations

import argparse
import math
import time
from typing import Any, Callable

from common import (
    add_common_args,
    cuda_times_ms,
    load_torch,
    require_h100,
    seed_everything,
    summarize_ms,
    validate_common_args,
    write_result,

def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser(description=__doc__)
    add_common_args(parser)
    parser.add_argument(
        "--case",
        choices=("sync", "launch", "memory", "compute"),
        required=True,
        help="Bottleneck mechanism to expose to the profiler.",
    )
    parser.add_argument(
        "--mode",
        choices=("baseline", "optimized"),
        required=True,
        help="Slow baseline or mechanism-matched candidate.",
    )
    return parser.parse_args()


def compile_and_warm(
    torch: Any, function: Callable[[], Any]
) -> tuple[Callable[[], Any], float]:
    compiled = torch.compile(function, fullgraph=True)
    started = time.perf_counter()
    compiled()
    torch.cuda.synchronize()
    return compiled, (time.perf_counter() - started) * 1_000


def build_sync_case(
    torch: Any, args: argparse.Namespace
) -> tuple[Callable[[], Any], Callable[[], Any], dict[str, Any]]:
    elements = 2_000_000 if args.profile == "smoke" else 16_000_000
    steps = 8 if args.profile == "smoke" else 40
    values = torch.randn(elements, device="cuda", dtype=torch.float32)

    def synchronized() -> float:
        total = 0.0
        for _ in range(steps):
            total += values.square().mean().item()
        return total

    def delayed() -> Any:
        reductions = [values.square().mean() for _ in range(steps)]
        return torch.stack(reductions).sum()

    selected = synchronized if args.mode == "baseline" else delayed
    return selected, delayed, {"elements": elements, "steps": steps}


def build_launch_case(
    torch: Any, args: argparse.Namespace
) -> tuple[Callable[[], Any], Callable[[], Any], dict[str, Any]]:
    elements = 262_144 if args.profile == "smoke" else 1_048_576
    steps = 12 if args.profile == "smoke" else 30
    values = torch.randn(elements, device="cuda", dtype=torch.float32)

    def pointwise_chain() -> Any:
        output = values
        for _ in range(steps):
            output = torch.tanh(output * 1.001 + 0.01)
        return output

    compile_ms = None
    selected = pointwise_chain
    if args.mode == "optimized":
        selected, compile_ms = compile_and_warm(torch, pointwise_chain)
    return (
        selected,
        pointwise_chain,
        {
            "elements": elements,
            "pointwise_steps": steps,
            "compiled_first_call_ms": compile_ms,
        },
    )


def build_memory_case(
    torch: Any, args: argparse.Namespace
) -> tuple[Callable[[], Any], Callable[[], Any], dict[str, Any]]:
    elements = 8_000_000 if args.profile == "smoke" else 64_000_000
    values = torch.randn(elements, device="cuda", dtype=torch.float32)
    bias = torch.randn(elements, device="cuda", dtype=torch.float32)

    def pointwise_pipeline() -> Any:
        hidden = values * 1.25 + bias
        gated = torch.nn.functional.silu(hidden) * hidden
        return torch.tanh(gated + 0.1)

    compile_ms = None
    selected = pointwise_pipeline
    if args.mode == "optimized":
        selected, compile_ms = compile_and_warm(torch, pointwise_pipeline)
    minimum_bytes = 3 * elements * values.element_size()
    return (
        selected,
        pointwise_pipeline,
        {
            "elements": elements,
            "compiled_first_call_ms": compile_ms,
            "minimum_input_output_bytes": minimum_bytes,
            "operation_count_note": (
                "No portable FLOP count is assigned to SiLU or tanh; use the "
                "profiler report for measured work and traffic."
            ),
        },
    )


def build_compute_case(
    torch: Any, args: argparse.Namespace
) -> tuple[Callable[[], Any], Callable[[], Any], dict[str, Any]]:
    width = 1_024 if args.profile == "smoke" else 4_096
    left_fp32 = torch.randn((width, width), device="cuda", dtype=torch.float32)
    right_fp32 = torch.randn((width, width), device="cuda", dtype=torch.float32)
    dtype = torch.float32 if args.mode == "baseline" else torch.bfloat16
    left = left_fp32.to(dtype=dtype)
    right = right_fp32.to(dtype=dtype)

    def selected() -> Any:
        return left @ right

    def reference() -> Any:
        return left_fp32 @ right_fp32

    useful_operations = 2 * width**3
    minimum_bytes = (left.numel() + right.numel() + width**2) * left.element_size()
    return (
        selected,
        reference,
        {
            "width": width,
            "dtype": str(dtype).removeprefix("torch."),
            "useful_operations": useful_operations,
            "minimum_input_output_bytes": minimum_bytes,
            "algorithmic_arithmetic_intensity_flop_per_byte": round(
                useful_operations / minimum_bytes, 4
            ),
        },
    )


def scalar_value(torch: Any, value: Any) -> float:
    if isinstance(value, (int, float)):
        return float(value)
    return float(value.detach().float().mean().item())


def main() -> None:
    args = parse_args()
    validate_common_args(args)
    torch = load_torch()
    environment = require_h100(torch)
    seed_everything(torch, args.seed)
    builders = {
        "sync": build_sync_case,
        "launch": build_launch_case,
        "memory": build_memory_case,
        "compute": build_compute_case,
    }
    workload, reference, case_metadata = builders[args.case](torch, args)

    samples = cuda_times_ms(
        torch,
        workload,
        warmup=args.warmup,
        iterations=args.iterations,
    )
    timing = summarize_ms(samples)

    with torch.cuda.nvtx.range("profile_region"):
        with torch.cuda.nvtx.range(f"{args.case}_{args.mode}"):
            observed = workload()
    torch.cuda.synchronize()
    expected = reference()
    torch.cuda.synchronize()

    error_metrics: dict[str, float] = {}
    if isinstance(observed, (int, float)):
        absolute_error = abs(float(observed) - scalar_value(torch, expected))
        equivalent = absolute_error <= max(1e-4, abs(float(observed)) * 1e-5)
        error_metrics["absolute_error"] = round(absolute_error, 8)
    elif args.case == "compute" and args.mode == "optimized":
        reference_norm = torch.linalg.vector_norm(expected.float()).clamp_min(1e-12)
        relative_l2_error = float(
            (
                torch.linalg.vector_norm(observed.float() - expected.float())
                / reference_norm
            ).item()
        )
        equivalent = relative_l2_error < 5e-2
        error_metrics["relative_l2_error"] = round(relative_l2_error, 8)
    else:
        equivalent = bool(
            torch.allclose(observed.float(), expected.float(), rtol=1e-4, atol=1e-4)
        )
    finite = (
        math.isfinite(float(observed))
        if isinstance(observed, (int, float))
        else bool(torch.isfinite(observed).all().item())
    )
    if not equivalent or not finite:
        raise SystemExit("The selected path failed its numerical equivalence gate.")

    median_seconds = timing["median_ms"] / 1_000
    measurements: dict[str, Any] = {
        "case": args.case,
        "mode": args.mode,
        "timing": timing,
        "profile_nvtx_range": "profile_region",
        "checksum": round(scalar_value(torch, observed), 8),
        **case_metadata,
    }
    operations = case_metadata.get("useful_operations")
    minimum_bytes = case_metadata.get("minimum_input_output_bytes")
    if operations:
        measurements["effective_workload_tflops"] = round(
            operations / median_seconds / 1e12, 4
        )
    if minimum_bytes:
        measurements["effective_minimum_io_gb_per_s"] = round(
            minimum_bytes / median_seconds / 1e9, 4
        )

    target = write_result(
        args,
        lab_id=f"14_profiler_bottlenecks_{args.case}_{args.mode}",
        environment=environment,
        measurements=measurements,
        correctness={
            "numerically_equivalent": True,
            "finite_output": True,
            **error_metrics,
        },
    )
    print(f"Completed {args.case}/{args.mode} profiler case: {target}")


if __name__ == "__main__":
    main()

"""Shared, dependency-light helpers for the GPU Optimization labs."""

from __future__ import annotations

import argparse
import json
import math
import os
import random
import re
import secrets
import statistics
from pathlib import Path
from typing import Any, Callable


def add_common_args(parser: argparse.ArgumentParser) -> None:
    parser.add_argument("--profile", choices=("smoke", "h100"), default="smoke")
    parser.add_argument("--seed", type=int, default=17)
    parser.add_argument("--warmup", type=int, default=5)
    parser.add_argument("--iterations", type=int, default=20)
    parser.add_argument("--output-dir", type=Path, default=Path("results"))


def validate_common_args(args: argparse.Namespace) -> None:
    if args.warmup < 0 or args.iterations < 1:
        raise SystemExit(
            "--warmup must be non-negative and --iterations must be positive"
        )
    # Lab artifacts can contain profiler and environment metadata. Keep newly
    # created files private even when a learner runs a lab outside Slurm.
    os.umask(0o077)
    args.run_id = resolve_run_id(getattr(args, "run_id", None))


def resolve_run_id(value: str | None = None) -> str:
    run_id = value if value is not None else os.environ.get("COURSE_RUN_ID")
    if run_id is None:
        run_id = secrets.token_hex(6)
    if re.fullmatch(r"[0-9a-f]{12}", run_id) is None:
        raise SystemExit("COURSE_RUN_ID must be exactly 12 lowercase hex characters")
    return run_id


def resolve_int_override(
    value: int | None,
    default: int,
    *,
    option: str,
    minimum: int = 1,
) -> int:
    resolved = default if value is None else value
    if resolved < minimum:
        raise SystemExit(f"{option} must be at least {minimum}")
    return resolved


def load_torch() -> Any:
    try:
        import torch
    except ImportError as exc:
        raise SystemExit(
            "PyTorch is required; follow the course environment setup."
        ) from exc
    return torch


def seed_everything(torch: Any, seed: int) -> None:
    random.seed(seed)
    torch.manual_seed(seed)
    if torch.cuda.is_available():
        torch.cuda.manual_seed_all(seed)


def require_h100(torch: Any) -> dict[str, Any]:
    if not torch.cuda.is_available():
        raise SystemExit(
            "CUDA is unavailable; this course requires an NVIDIA H100 GPU."
        )
    props = torch.cuda.get_device_properties(torch.cuda.current_device())
    if (
        "H100" not in props.name
        or "MIG" in props.name.upper()
        or (props.major, props.minor) != (9, 0)
    ):
        raise SystemExit(
            f"Expected one full H100 (SM90); detected {props.name!r} "
            f"with compute capability {props.major}.{props.minor}."
        )
    return {
        "gpu_family": "NVIDIA H100",
        "compute_capability": "9.0",
        "memory_gib": round(props.total_memory / 2**30, 1),
        "torch_version": torch.__version__,
        "cuda_version": torch.version.cuda,
    }


def cuda_times_ms(
    torch: Any,
    operation: Callable[[], Any],
    *,
    warmup: int,
    iterations: int,
) -> list[float]:
    for _ in range(warmup):
        operation()
    torch.cuda.synchronize()
    samples: list[float] = []
    for _ in range(iterations):
        start = torch.cuda.Event(enable_timing=True)
        end = torch.cuda.Event(enable_timing=True)
        start.record()
        operation()
        end.record()
        end.synchronize()
        samples.append(float(start.elapsed_time(end)))
    return samples


def summarize_ms(samples: list[float]) -> dict[str, float]:
    ordered = sorted(samples)
    p90_index = max(0, min(len(ordered) - 1, math.ceil(0.9 * len(ordered)) - 1))
    return {
        "median_ms": round(statistics.median(ordered), 4),
        "min_ms": round(ordered[0], 4),
        "p90_ms": round(ordered[p90_index], 4),
    }


def write_result(
    args: argparse.Namespace,
    *,
    lab_id: str,
    environment: dict[str, Any],
    measurements: dict[str, Any],
    correctness: dict[str, Any],
) -> Path:
    failed_checks = sorted(key for key, value in correctness.items() if value is False)
    if failed_checks:
        raise SystemExit("Failed correctness checks: " + ", ".join(failed_checks))
    run_id = resolve_run_id(getattr(args, "run_id", None))
    target = args.output_dir / f"{lab_id}-run-{run_id}.json"
    payload = {
        "schema": "gpu-course-result/v1",
        "lab_id": lab_id,
        "profile": args.profile,
        "run_id": run_id,
        "seed": args.seed,
        "environment": environment,
        "measurements": measurements,
        "correctness": correctness,
    }
    document = json.dumps(payload, indent=2, sort_keys=True) + "\n"
    args.output_dir.mkdir(mode=0o700, parents=True, exist_ok=True)
    flags = os.O_WRONLY | os.O_CREAT | os.O_EXCL
    try:
        descriptor = os.open(target, flags, 0o600)
    except FileExistsError as exc:
        raise SystemExit(f"Refusing to overwrite an existing result: {target}") from exc
    with os.fdopen(descriptor, "w", encoding="utf-8") as stream:
        stream.write(document)
    return target


def configure_slurm_distributed_env() -> tuple[int, int, int]:
    rank = int(os.environ.get("RANK", os.environ.get("SLURM_PROCID", "0")))
    world_size = int(os.environ.get("WORLD_SIZE", os.environ.get("SLURM_NTASKS", "1")))
    local_rank = int(os.environ.get("LOCAL_RANK", os.environ.get("SLURM_LOCALID", "0")))
    os.environ.setdefault("RANK", str(rank))
    os.environ.setdefault("WORLD_SIZE", str(world_size))
    os.environ.setdefault("LOCAL_RANK", str(local_rank))
    return rank, world_size, local_rank


def init_nccl(torch: Any, *, expected_world_size: int = 2) -> tuple[int, int, int]:
    rank, world_size, local_rank = configure_slurm_distributed_env()
    if world_size != expected_world_size:
        raise SystemExit(
            f"Expected {expected_world_size} ranks; use slurm/two_node.sbatch."
        )
    for required in ("MASTER_ADDR", "MASTER_PORT"):
        if not os.environ.get(required):
            raise SystemExit(f"{required} is missing; use the supplied Slurm launcher.")
    torch.cuda.set_device(local_rank)
    torch.distributed.init_process_group(backend="nccl", init_method="env://")
    return rank, world_size, local_rank


def close_distributed(torch: Any) -> None:
    if torch.distributed.is_available() and torch.distributed.is_initialized():
        torch.distributed.destroy_process_group()
