01

Start with trusted inputs

Intake & eligibility

Next: Review & repair ↗

Every request enters the same controller. Scope, policy and the current PR revision determine what can happen next.

↳Closure is available only to full-process requests in repair or merge mode. A review-only request never closes a PR.

The flow, in words

  1. Admit new work once

    General admission enrolls only newly opened PRs in the current enabled epoch. During qualification, only exact maintainer-selected candidates and capabilities are permitted; ordinary automatic intake stays off. New drafts wait for readiness. Existing PRs require a manual PR-number request.

  2. Preserve request intent

    Update, reopen and readiness events resume only an already-active request. Review-only requests cannot gain repair, closure or merge authority. Terminal requests require a fresh manual dispatch; reruns do not reset them.

  3. Retain bounds

    A request keeps its original three-hour deadline, two repair attempts and capability ceiling. Recovery resumes active execution and retained completion obligations; it never scans an open-PR backlog or restarts terminal execution.

  4. Proceed with identity

    Bind both repository identities, head ref, current head/base/tree and request ID before assessment. Canary permits also bind expiry and generation. A changed head or base, including an agent repair, requires a renewed canary permit.

02

Bounded correction, fresh evidence

Review & repair

Next: Qualification & merge ↗

Review the code and branch readiness. When a correction is allowed, publish it through the trusted owner and start qualification again.

↳Report mode and explicit review-only requests end after review. Repair mode can continue through qualification, but cannot merge. Repairs are bounded by two attempts and the original three-hour PR-operation deadline.

The flow, in words

  1. Establish usefulness

    Check objective redundancy, then assess the complete contribution against the accepted baseline, PR explanation and human discussion. Useful small changes qualify. Uncertainty leaves the PR open.

  2. Corroborate no benefit

    No-benefit closure needs a separate blind assessment of the same evidence. Changed rationale or conflicting human review blocks closure. Revalidate before and after the effect; never undo an unowned human closure.

  3. Repair conservatively

    For useful changes, same-repository conflicts can receive at most five agent-edited files and 200 changed non-marker lines, excluding clean base changes. Preserve both intents. Independent review, alignment and trusted focused checks must pass before publication. Large conflicts can use one attributed replacement PR with inherited limits. The original fork is never written.

  4. Review, align and route

    Run review-pr, code-review and align with observed check receipts. Requalify every repaired head. Review-only or default-disabled fork merge requests end with an explanation. Eligible requests continue to CI, then live qualification.

03

Evidence for one exact revision

Qualification & merge

Next: Release coordination ↗

Candidate CI, then live behavior, cleanup and GitHub protections come together at an independent merge gate.

↳A lifetime waiver survives commits and reopenings until revoked. It can waive missing validation. Failed or intervened trials, defects, review, CI and cleanup remain blocking.

The flow, in words

  1. Run candidate CI first

    Required CI is admitted by a trusted controller artifact and binds the active request, both repositories, head/base/tree and producer. Cached review/alignment evidence is reused only while its complete identity remains valid.

  2. Apply live policy

    After CI passes, assess live applicability. An eligible waiver may skip missing validation; failed trials require diagnosis, bounded repair and a fresh trial. Inapplicable or unavailable validation routes to manual merge only without known blockers. Cleanup remains required.

  3. Revalidate merge authority

    Require successful current evidence, cleanup, original request authority, current mode/fork restrictions and GitHub protections. A false-to-true fork setting does not upgrade an active request. Fork branch edits require the contributor; an authorized repository-owned replacement can receive bounded repairs.

  4. Merge and verify

    The protected merge broker checks again before approval and merge. No fork branch write or protection bypass is allowed. Confirm the merged result before release coordination.

04

One owner from version to publication

Release coordination

Next: Operating rules ↗

Automatic and laptop requests use one release coordinator. Original evidence and a durable reservation protect the entire publication.

↳Manual requests repeat release enablement and exact merged-result CI checks. Publication succeeds only after downloaded assets match the original hashes; failed verification never becomes a public-success claim.

The flow, in words

  1. Qualify the merged result

    Required CI must pass on the exact merge result. Otherwise record the blocker and do not publish.

  2. Decide whether a release is needed

    Automatic intake continues only when releases are enabled and an enrolled package is affected. Otherwise complete without a release. A laptop request enters the same coordinator with verified merge evidence and the same gates.

  3. Reserve and build

    Acquire the package lock and read immutable release fragments. During qualification, require an exact project/source/version permit before reserving the tag. Build without write credentials; invalid package identity or asset hashes block publication.

  4. Publish with recovery

    During qualification, require a separate exact asset-manifest permit tied to preparation. Upload draft assets, verify downloaded hashes, then make the release public. Retain the reservation and evidence for recovery. A successful path ends at “Release published & verified.”

Boundaries that apply everywhere

Automation has explicit limits.

GitHub-hosted runners orchestrate the workflow. Two evaluator slots bound model work; a separate supervisor persists accepted evidence, and one durable reservation serializes live trials. Nebius supplies inference and disposable test targets. Agents propose work; trusted owners authorize effects.

Execution modes
ModeWhat it permits
DisabledNo new PR automation is admitted. Owned recovery and cleanup remain separate responsibilities.

Forks are identified, merging is opt-in

The source:fork label and updated bot comment retain origin. AI_AUTOMATION_MERGE_FORK_CONTRIBUTION defaults false; true enables eligibility only. No fork branch writes are permitted. Cancel queued/running jobs for an immediate stop after disabling.

One authority, wherever a request starts

Laptop skills and hosted runners share effect owners and durable locks. They do not create competing merge or release paths.

Review-only always stays review-only

An explicit review request does not gain repair, closure or merge authority from the configured mode.

A waiver is narrow and durable

It belongs to one immutable PR and survives new commits and reopenings until revoked. Review, CI, identity, protections and cleanup still apply.

Failure keeps the gates closed

Unsupported or failed admitted processing leaves the PR open. Maintain/Admin operators select exact canaries and explicitly enable general admission after qualification. GitHub protections remain authoritative.

A release follows package impact

Enrolled packages are vpngw and nebius-cxcli. Documentation or test-only changes do not create a release. Immutable fragments determine the next version.

Recovery keeps its original evidence

Durable reservations resume interrupted publication. Recovery rechecks live ownership under both leases before cleanup; stale observations cannot clean a successor. Unknown writers retain capacity. Failed or intervened evidence cannot become a pass.

Runtime images and same-repository rehearsal. AI_AUTOMATION_CODEX_VERSION defaults to latest or accepts an exact pin. Automatic hourly image work requires AI_AUTOMATION_IMAGE_PUBLISH=true; manual runs can qualify without publishing. Every build freezes one version and integrity before qualification. A maintainer selects the immutable digest; each PR pulls it. The read-only qualification workflow assesses an existing PR without comments or production admission. Report mode may comment and is not that rehearsal.

PR and issue completion

Each selected PR receives an evidence-based status. Large conflicts use one replacement with feature commits and inherited limits. Close the original only after verified merged coverage. Assess linked issues independently: rejection does not resolve them. Preserve human reopening and verify current merged behavior before explicit closure.
