01 / The idea

One branch.
Many projects.
Managed for you.

Start an objective in each project. Implement or SDLC creates the isolated checkouts, coordinates workers, validates the result, integrates it, and cleans up.

feature/example-branch1 collects completed work and remains your delivery branch.

Independent sessions

0

Worktree names to track

Start, inspect status, and continue using the original project folders.

A branch is a moving reference to a commit. A worktree is a checkout with its own files, index, and HEAD. Linked worktrees share Git objects and references; they are not security sandboxes.

02 / Start two projects

Use the folders you already know.

Begin on a named non-default branch with a clean selected project and clean shared inputs. Open separate native agent sessions in the two project folders.

Session A · project-a

Working directory: /repo/project-a

$implement Add paginated search with focused tests and documentation.

The coordinator creates an outer worktree for this objective and freezes its inner source.

Session B · project-b

Working directory: /repo/project-b

$implement Add JSON export with focused tests and documentation.

This objective owns its own outer, integration checkout, tasks, and completion receipts.

Check both projects

$implement status

From the repository root, see objectives, owners, phases, workers, and waiting reasons.

Return another day

$implement continue /repo/project-a

The workflow finds the recorded objective without a generated branch or checkout name.

For the full phase-driven lifecycle, use $sdlc-start <objective> in either project. Continue with the same workflow owner. Every new objective receives a fresh outer.

Unrelated sibling folders may have staged, unstaged or untracked work. The coordinator declares the committed inputs before excluding that dirt. Dirty selected-project files, effective instructions, canonical specs or shared dependencies block startup. No dirty content enters the outer. Manual Worktree creation still requires a wholly clean source.

03 / Ownership

One objective. Separate workspaces.

The original branch can keep moving while an objective is built and checked in isolation. “Nested” describes ownership, not directories.

Independent projects use separate native sessions and separate outers. Shared paths, ports, containers and databases still require coordinated ownership.

04 / Responsibilities

A stable target. A working candidate.

The outer and integration worktrees have different lifetimes and acceptance boundaries.

Outer versus integration
AspectOuter worktreeIntegration worktree
RoleObjective branch and delivery anchorAssembles and validates one execution
During inner executionStays at the recorded baseAdvances with admitted task results
After validationReceives the sealed commit; remains through delivery or recoveryRemoved after verified promotion

Promotion requires a clean outer on the recorded branch at the expected base. A replay may observe the exact already-promoted commit; it does not merge twice.

Before acceptance

Outer:       A
Integration: A → task results → B
Checks fail: B stays isolated

After acceptance

Checks pass: outer advances A → B
Integration: cleaned up
Outer:       retained for final delivery

SDLC performs its post-promotion UAT and documentation assessment against the promoted project checkout. Corrections preserve earlier evidence and use a fresh execution.

05 / Workers & waves

Parallel tasks. Ordered integration.

A dependency wave groups tasks that can start from the same frozen base. Worker slots refill as completed results are admitted.

Admit, then refill

Verify results, native termination, and runtime lease release before freeing a slot.

Keep the barrier

The next dependency wave starts only after the entire prior wave is integrated and validated.

Share fairly

Ready objectives rotate at completed wave boundaries. Waiting work keeps its identity and evidence.

06 / Integration

Deliver against the latest aggregate.

The aggregate may advance while projects work. Integration validates the actual combination before moving the source branch.

  1. Finish internally. Validated workers integrate into the coordinator checkout, then the outer.
  2. Fence child writes. Enter aggregation-ready while retaining ownership.
  3. Wait for a clean original. Keep the completed outer while unrelated source work is unfinished.
  4. Reserve delivery. Freeze current original and outer heads; build a separate two-parent candidate.
  5. Validate the combination. Run frozen acceptance and required alignment/UAT against that exact candidate.
  6. Promote and record proof. Fast-forward only to the validated SHA. Source drift invalidates promotion.
  7. Release and clean up. Persist receipts, release leases, remove exact owned resources, and verify absence.

A useful timeline

Aggregate begins at C0
  ├─ A starts from C0
  ├─ B starts from C0
  └─ ordinary work advances it to C1

A candidate = C1 + A result
  → checks pass → aggregate becomes M1

B candidate = M1 + B result
  → checks pass → aggregate becomes M2

B’s result remains usable, but its final acceptance covers the new combination at M2.

Only one candidate owns aggregate promotion at a time. Other projects can keep executing while waiting for delivery.

07 / Recovery

Waiting is a recorded state.

The workflow retains ownership and evidence when it cannot proceed. Resume from the original project folder.

What happens when conditions change
ConditionWorkflow responseYour next step
Aggregate advancesRebuild against its current descendant head; at most two automatic drift rebuilds after the initial candidate.Usually none. An exhausted budget returns an explicit retry decision.
Dirty or switched sourceWait without committing, stashing, or switching unrelated work.Finish source work, return to the recorded branch, then run the owning workflow’s continue command.
Combined checks failPreserve failed evidence; diagnose and create a fresh corrective execution revision.Answer unresolved product decisions.
Session closesDurable state survives. No daemon keeps operating.Use the workflow’s continue command.
Cleanup is interruptedReconcile exact delivery and remaining resources without merging twice.Continue from the original folder.
Source history is rewrittenBlock because recorded identity or ancestry no longer holds.Resolve the source decision explicitly.

Failed trials remain failed. Recovery never erases them. Cancellation preserves unmerged work and does not undo delivered commits.

Delivery pending: your next command

The final message names the original branch, retained work and blocker. After the entire original checkout is clean, run the command for the owning workflow:

Implement objective
$implement continue "project-a"
SDLC objective
$sdlc-start continue "project-a"

Replace project-a with the original project path. From that folder, bare continue is sufficient. Each actual run reports only its own command. The workflow never commits, stashes or discards unrelated work.

If promotion already happened, the message says finalization or cleanup pending. If proof is incomplete, it says verification or recovery pending. Completed delivery needs no continuation command.

08 / Shipping

Publish completed aggregate work.

Commit, push, and PR workflows operate on the aggregate under their existing authorization. Automatic local integration is a separate boundary.

While objectives are active

  • Ordinary source work can advance the aggregate.
  • Commit and publication effects wait for an active integration reservation.
  • Each child keeps its frozen execution basis.
  • Later candidates validate against the updated source.

When opening or merging a PR

  • Review actual aggregate content and its commit SHA.
  • Publish through the existing guarded workflow.
  • Keep the aggregate branch and history while objectives depend on it.
  • After squash merge, use ordinary guarded synchronization before another PR cycle.

Pushing the aggregate backs up commits reachable from that branch. It does not back up unfinished commits that exist only on local child branches.

Git references and objects are shared. Deleting or rewriting branches can affect other worktrees. Separate working files do not imply independent repository history.

GitHub explains the repeated-commit and conflict considerations of squash-merging long-running branches. Follow the repository’s permitted merge policy.

09 / Limits & proof

Small enough for everyday use.

One execution host and one selected native installation share admission. The workflow manages resource names; you manage objectives.

One outstanding objective owns each project. Sibling folders may run concurrently. Equal, ancestor, descendant, and repository-wide scopes conflict; shared writes require claims before editing.
